# 現行系統的完整測試資料

`GAS/testData.gs` 已配合現在的欄位與流程更新：取消與改期立即完成，退費仍由管理員處理，並包含考後出席及成績。產生器每次追加一批 `TD_` 開頭的資料，不會清空 Exam、Reserved、Transaction 或其他工作表，也不改動既有會員的身分、GoogleSub、個人資料或提醒偏好。

執行一次就會連同會員、科目、場地、場次、預約、付款交易、退款申請、退件備註、成績、通知、提醒偏好與管理操作紀錄一起產生。可以在空白測試試算表建立全部 12 張業務資料表；不需要先手動建立場地或場次。

資料分為兩部分：固定情境可逐項驗收特殊流程；一般營運資料則讓六個科目各有三個未來場次、一個歷史場次，分散到五個場地。未來日期延伸至約兩個月後，歷史紀錄涵蓋約一至兩個月前，可以測試科目／場地／日期篩選、名單、容量、成績與統計。場地地址及付款資料皆為虛構測試內容。

## 使用方式

1. 把更新的 `testData.gs` 放入目前完整的 Apps Script 專案。它使用現有 `Config.gs`、Sheet helpers 及報名功能，不能單獨執行。先確認 `SPREADSHEET_ID` 指向準備驗收的測試試算表。
2. 用自己的 Google 帳號登入測試網站一次，讓 Users 有該會員的真實 GoogleSub。若要在「我的考試」看到整套情境，在 Script Properties 設定 `TEST_DATA_VIEWER_EMAIL` 為這個已註冊會員的 email；也可以直接填 `TEST_DATA_OPTIONS.VIEWER_EMAIL`。會員不存在時會中止，不會假造 Google 身分或新增假管理員。
3. 執行 `previewTestData()`，在執行記錄查看新增筆數、主要考生及情境清單。這個函式只讀取現有表，不建表、補欄位、寫資料、建檔或寄信。
4. 執行 `generateTestData()`。缺少的表／新欄位由既有 helper 建立或追加；欄位順序不符時中止。執行完成會回傳 batchID、各表新增筆數與每個情境的 reserveID／examID。預覽與生成是不同批次，請以生成結果的序號查詢。
5. 重新整理網站，在首頁科目／考場篩選選取新生成的 `[測試]` 項目；部分場次在下個月，歷史場次在前一至兩週。管理端可用 `TD_` 序號搜尋申請及操作紀錄。

沒有設定主要考生時，資料會掛在 `learner001@nutsreserve-test.invalid`。假會員只用於名單、容量與統計，不能用來 Google 登入；這種模式可由原有管理員查看整批資料，自己的「我的考試」不會出現這些假會員資料。

## 預設產量

| 工作表 | 每批新增 |
| --- | ---: |
| Users | 首次 12；之後重用相同假會員 |
| Subject / Room | 6 / 5 |
| Exam | 40（16 個情境場次與 24 個營運場次） |
| Reserved | 175（41 筆情境／額外名單與 134 筆營運預約） |
| Transaction / Comments / Notice | 134 / 2 / 1 |
| ReservationRequests | 10 |
| AuditLog | 423 |
| Notifications | 498（148 筆示範及 350 筆排程防護） |
| NotificationPreferences | 首次 12；已有資料不覆寫 |

每次執行會保留前一批並新增獨立序號，不會重設之前操作過的測試情境。反覆生成會累積資料，建議在專用測試試算表操作。

預覽及生成結果也會列出科目、場地容量／場次数、收款與退款摘要。預設金流如下，皆為模擬金額，**不會真的扣款、轉帳或退款**：

| 金流項目 | 預設金額／筆數 |
| --- | ---: |
| 已確認收款 | NT$71,200（113 筆 PAID 交易） |
| 已退款 | NT$480 |
| 淨收款 | NT$70,720 |
| 有效預約未收餘額 | NT$61,800 |
| 待審付款證明金額 | NT$15,400（20 筆 PENDING 交易） |
| 退件交易 | 1 筆 FAILED |

待審金額仍包含在未收餘額內，審核通過後才算已收款。退款以申請的核准金額、退款憑證和報名的 refundedAmount 記錄，符合目前後端；不另造一筆不存在的負數付款交易。一般營運資料包含兩筆交易付清同一預約的情境，每筆預約的已確認交易合計都與 paidAmount 相符。舊資料推估情境仍保留空白快照，以便驗收報表標記。

## 情境對照

reserveID 結尾包含下列代碼，執行結果也會列出完整序號。

| 代碼 | 可以驗收的行為 |
| --- | --- |
| REVIEWING / REGISTRATION_REJECTED | 待審報名、退件原因、修改後重審 |
| UNPAID / PAYMENT_PENDING / PAYMENT_REJECTED | 待繳費、私人證明查看、付款審核、證明退件後重傳 |
| PARTIAL_PAID / PARTIAL_PENDING | 部分付款、未付餘額、另一筆證明待審，PAID 交易加總等於 paidAmount |
| PAID | 已付款、英文考試及加購費用、日曆及確認單 |
| CANCELLED_UNPAID | 取消立即完成，不再占用名額，保留申請／稽核紀錄 |
| RESCHEDULED_UNPAID / RESCHEDULED_BALANCE | 已改到同科目場次；後者保留原已付款並需補繳較高費用 |
| REFUND_PENDING / PROCESSING / APPROVED | 待處理、處理中、已核准待退款；可接續管理員流程 |
| REFUND_COMPLETED / REJECTED / WITHDRAWN | 已完成部分退款並取消、拒絕、考生撤回；包含歷程、版本及退款憑證 |
| LEGACY_ESTIMATED | 沒有金額快照的舊已付款資料、報表推估標記及核准退費前要求核對金額 |
| FEE_SNAPSHOT | 場次調價後原報名仍保留 600 元快照 |
| FREE_APPROVED | 零元場次已通過審核且無需付款，沒有假的零元轉帳 |
| RESULT_PASS / RESULT_FAIL / ABSENT | 已應考通過、未通過、缺考；缺考沒有分數或結果 |
| RESULT_PENDING / RESULT_NOT_RECORDED | 已出席但未公布分數，以及管理員尚未登記成績 |
| EXPIRED_UNPAID | 考試已結束但未付款的歷史紀錄 |
| PAYMENT_DUE / EXAM_SOON | 12 小時後付款截止、18 小時後考試；通知中心可查看提醒示範 |
| EXAM_CANCELLED_PAID / CLOSED_PAID | 學苑取消場次但尚待退款，以及停止新報名後保留的已付款報名 |
| DEADLINE_UNPAID | 尚未開考但報名／付款期限已過 |
| FULL_0–3 / ROSTER_0–5 | 四人額滿場次、多會員名單及 CSV 匯出 |
| SESSION_科目_輪次_BOOK_名單序號 | 各場地的一般營運預約：待審、未付、付款待審、付清、部分付款及分次付清 |
| HISTORY_科目_3_BOOK_名單序號 | 歷史考試預約與付款，包含通過、未通過及缺考 |

另外包含 Draft 場次及訂閱紀錄、完全沒有報名的 EMPTY 場次、不同科目改期排除，以及低／高費用的同科目目標。日期由執行當下依台北日曆計算，不受 Apps Script 專案時區影響。

## 圖片與通知

- 預設建立一張私人 1×1 PNG，所有這批模擬交易共用該圖片的 fileID。它用來測試私人證明 API，**不是銀行單據或已付款依據**；不使用外部圖片網址，也不建立公開分享連結。需有付款資料夾的寫入權限，並將資料夾設為 PRIVATE。
- 不需要圖片時，將 `CREATE_PAYMENT_PROOF` 改為 false，或設定 Script Property `TEST_DATA_CREATE_PAYMENT_PROOF=false`。此時只生成表格資料，證明查看會顯示檔案尚不存在；可自行上傳一筆測試圖片接續驗收。
- 產生器不呼叫 MailApp、不安裝或移除排程。示範 sent／failed 為模擬歷史；queued 安排在一百年後，failed 已達三次嘗試，防止現有排程寄出示範信。
- 每筆報名另外放入兩筆 skipped 通知，使用正式排程的付款／考前提醒去重鍵，阻止現有排程自動產生這批測試報名的提醒。這些防護列在管理員發送紀錄可見，考生通知中心會排除。
- **後續在網站實際審核、改期、登記成績、修改場次或截止時間，仍會依正式功能建立新的通知。** 若要驗收真實寄信，使用專用測試環境與可接收信的測試會員，並自行控制排程；不要把產生器的防護當成全專案停寄開關。
- 寫入中途失敗時復原本次涉及的表，並把這次新建的測試圖片移到垃圾桶。沒有刪除既有資料或其他 Drive 檔案。Apps Script 執行被強制終止時仍可能留下部分資料，需用 batchID 人工核對。

可調整 `TEST_DATA_OPTIONS` 的基本費用（至少 100）、假會員數（4–100）、額外名單筆數（0–100）及 `RESERVATIONS_PER_SESSION` 每個營運場次的人數（1–50，預設 6）。實際名單上限取設定人數、場地容量及假會員數的最小值，同一營運場次不會重複使用同一考生。上述筆數與金額會隨設定變動。固定情境則會集中在主要考生，方便一次查看各種流程狀態。退款範例使用 80% **只為示範部分退款**，不代表學苑的退費政策。

## 本機驗證

執行 `npm test`。新增測試涵蓋唯讀預覽、已註冊考生指定、既有資料保留、重複執行、名額及金額一致、申請歷程、私人證明、實際 handler 接續操作、排程不寄 fixture、故障復原與跨年台北日期。所有操作在 Node 的 GAS 模擬環境執行，沒有對正式 Google Sheets／Drive／Mail 操作。
